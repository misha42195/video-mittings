# Plan: Загрузка файлов встречи

**PRD:** docs/prd-meeting-file-upload.md
**Дата:** 2026-08-24

### Фаза 1: Backend Tracer Bullet — модель, хранение и базовые эндпоинты

**Цель:** Минимально рабочий API загрузки/списка файлов с сохранением на диск и в БД
**Затрагивает:** backend / database

**Задачи:**
- [x] Написать e2e-тесты фазы: `POST /meetings/{id}/files` (успех, 400 тип/размер, 404 чужой), `GET /meetings/{id}/files` (пусто/после загрузки), проверка записи в БД и на диске — должны падать до реализации
- [x] Создать модель `MeetingFile` + миграцию (поля: id, meeting_id FK, filename, content_type, size, storage_path, created_at)
- [x] Реализовать локальное хранение на диске (директория `storage/meetings/{id}/`, генерация уникального имени, потоковая запись)
- [x] Реализовать `POST /meetings/{id}/files` — валидация типа (mp4/mov/wav/mp3/pdf/docx) и размера ≤100МБ → 400, проверка владения → 404
- [x] Реализовать `GET /meetings/{id}/files` — список с метаданными, проверка владения → 404

**Когда готова:** e2e-тесты фазы зелёные: `curl` загрузка проходит, запись в БД/на диске, `GET /files` возвращает список, негативные кейсы 400/404

### Фаза 2: Frontend — секция "Файлы" на странице встречи

**Цель:** Пользователь видит список файлов и может загрузить файл с прогрессом
**Затрагивает:** frontend

**Задачи:**
- [x] Написать e2e-тесты фазы (Playwright): секция "Файлы" рендерится, загрузка с прогресс-баром, список обновляется, ошибка 400 показывается — падают до реализации
- [x] Сверстать секцию "Файлы" внутри страницы встречи (список: имя, размер, дата, тип-иконка + empty state)
- [x] Добавить кнопку/инпут загрузки одного файла с индикатором прогресса (xhr/fetch onUploadProgress)
- [x] Подключить к API `POST/GET /meetings/{id}/files`, обработка ошибок валидации (показ сообщения из 400)

**Когда готова:** e2e-тесты фазы зелёные: секция видна, загрузка через UI с прогрессом, список обновляется без перезагрузки, ошибки отображаются

### Фаза 3: Скачивание и удаление (стриминг + права)

**Цель:** Полный жизненный цикл файла — скачать и удалить с проверкой прав
**Затрагивает:** backend / frontend

**Задачи:**
- [x] Написать e2e-тесты фазы: `GET .../download` стрим + `Content-Disposition: attachment` + 404 чужой, `DELETE` (успех, 404, отсутствие на диске/БД), UI кнопки скачать/удалить — падают до реализации
- [x] Реализовать `GET /meetings/{id}/files/{fileId}/download` — стриминг с диска (`StreamingResponse`/`FileResponse`), без загрузки в память, проверка владения → 404
- [x] Реализовать `DELETE /meetings/{id}/files/{fileId}` — только владелец, удаление с диска + из БД, чужой → 404
- [x] Добавить в секцию "Файлы" кнопки "Скачать" (всем) и "Удалить" (только владельцу, с подтверждением)

**Когда готова:** e2e-тесты фазы зелёные: скачивание стримом, удаление чистит диск+БД, 404 на чужой ресурс

### Фаза 4: Полировка и расширенные тесты

**Цель:** Довести фичу до критериев готовности PRD, закрыть UX-края
**Затрагивает:** backend / frontend

**Задачи:**
- [ ] Написать e2e-тесты фазы: полный сценарий загрузка→список→скачивание→удаление→проверка отсутствия + негативные кейсы + состояния пусто/загрузка/ошибка сети — падают до реализации
- [ ] Унифицировать тексты ошибок валидации и ответы 404 для всех эндпоинтов файлов
- [ ] Добавить состояния загрузки/пустого списка/ошибки сети в UI секции "Файлы"
- [ ] Проверить потоковую отдачу больших файлов до 100МБ (не грузить в память)

**Когда готова:** e2e-тесты всех фаз зелёные, все 7 чекбоксов "Критерии готовности" PRD закрыты, `npm run test` / `pytest` проходят

## Правила разбивки на фазы:
- Каждая фаза даёт рабочий результат, можно остановиться после любой
- Фаза 1 — Tracer Bullet (backend-минималка без фронта, но с API)
- ≤5 задач в фазе, бэкенд и фронтенд разнесены (фазы 1 и 2, частично 3)
- Каждая фаза начинается с e2e-тестов (красные до реализации, зелёные = готовность)
- План покрывает все 7 критериев готовности PRD, задач вне PRD нет
