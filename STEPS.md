5. **Определение технологий для модуля регистрации/авторизации.** Перед реализацией согласованы (уточняющими вопросами пользователю) и применены следующие технологии, с обоснованием:
   - **Вид тестов — API e2e (`pytest` + `httpx.AsyncClient`)**, а не браузерный Playwright: у auth-логики нет UI, тесты гоняются напрямую против ASGI-приложения (`ASGITransport`) и реального Postgres из `docker-compose.yml` (без моков БД) — это и есть цель e2e для backend-фичи.
   - **SQLAlchemy 2.0 (async, `DeclarativeBase`/`Mapped`/`mapped_column`) + `asyncpg`** — стандартный async ORM/драйвер для FastAPI, БД уже поднята через `docker-compose.yml` (Postgres 17).
   - **`bcrypt`** для хеширования паролей напрямую (без `passlib`, так как тот не поддерживается активно).
   - **`pyjwt`** для выпуска JWT (вместо `python-jose`, который менее активно поддерживается).
   - **`pydantic-settings`** для конфигурации через `.env` (`DATABASE_URL`, `JWT_SECRET_KEY` и т.д.) — стандартный подход в FastAPI-проектах.
   - **Подход разработки — TDD**: сначала написаны падающие e2e-тесты по сценарию (регистрация → JWT, логин по email+паролю → JWT, ошибочные случаи), затем — реализация, чтобы тесты стали проходить.
   - **Архитектура модуля — CQRS** (по отдельному запросу пользователя): `commands.py` (`RegisterUserCommand`/`RegisterUserHandler` — запись) отделён от `queries.py` (`AuthenticateUserQuery`/`AuthenticateUserHandler` — чтение, логин не меняет состояние БД), роутер (`routers/auth.py`) остался тонким и переводит доменные исключения (`exceptions.py`) в HTTP-ответы. Это дало возможность тестировать бизнес-логику отдельно от HTTP-слоя (`tests/test_auth_handlers.py`), не переусложняя при этом остальной проект (без отдельных БД на чтение/запись, без event sourcing — это было бы избыточно для одного auth-модуля).
